# 合并、清理、发布功能说明

本工具用来处理「根仓库 + 多层子模块」的分支合并。界面上主要有三页：**合并**、**清理**、**发布**（把结果推到远端）。

建议顺序：仓库不干净时先清理 → 再合并 → 确认结果后发布。

---

## 合并

把一条来源分支合进当前工作分支。工具会自动处理子模块指针冲突；普通文件冲突会打开你配置的冲突工具，让你手动改。

使用前：根仓库和所有子模块的工作区必须干净（没有未提交改动）。一次只合并一个分支。

大概过程：

1. 按你选的基准创建或使用工作分支。
2. 把来源分支合进来。
3. 子模块冲突由工具自动递归处理；普通文件冲突交给冲突工具。
4. 全部解决后，由工具生成合并提交。
5. 遇到工具无法自动处理的冲突时，会**暂停并保留现场**。你改完并 `git add` 后，点「继续合并」。不想继续则点「终止合并」。

「终止合并」只把本次合并涉及的仓库恢复到开始前，**不会删除未跟踪文件**。若要把整个仓库洗干净以便重新合并，请用「清理」。

### 合并里最关键的 Git 命令

| 命令 | 一句话说明 |
|---|---|
| `git merge --no-ff --no-commit` | 把对方分支合进当前仓库，先不自动提交，方便工具继续处理冲突。 |
| `git mergetool`（或你配置的冲突工具） | 打开编辑器，帮你解决普通文件里两边都改过的内容。 |
| `git add` | 把已经解决好的文件或子模块记入暂存区，表示“这里处理完了”。 |
| `git commit` | 生成这次合并提交。工具会在冲突全部解决后自动执行，一般不必自己提交。 |

## 清理

把仓库恢复成可重新合并的干净状态。它会递归处理根仓库和子模块。

**这是破坏性操作。** 未提交的修改、已暂存内容和未跟踪文件都可能被丢掉。需要保留的内容请先自行提交或另存。界面会要求确认；命令行非交互模式必须加 `--yes`。

清理大致会做这些事：中止进行中的合并/变基、把已跟踪文件打回最近一次提交、删掉多余未跟踪文件，再按当前提交把子模块对齐。某一步不够干净时，会自动用更强的方式再试。

可选：清理后重建工作分支。默认还会删掉上次暂停留下的 `merge_manual_todo.txt`。

和「终止合并」的区别：终止合并只撤销当前这一次合并；清理是整仓强力复位，不依赖是否正在合并。

### 清理里最关键的 Git 命令

| 命令 | 一句话说明 |
|---|---|
| `git merge --abort` / `git rebase --abort` | 取消正在进行的合并或变基，回到该操作开始前。 |
| `git reset --hard HEAD` | 丢弃已跟踪文件的未提交修改，工作区回到最近一次提交。 |
| `git clean` | 删除未被 Git 跟踪的文件和目录（默认不删被忽略的文件）。 |
| `git submodule update --init --recursive` | 按当前提交把各层子模块内容重新下载并对齐。 |

## 发布（推送）

把当前根仓库 HEAD，以及它记录的子模块提交，推到你指定的远端分支。

发布以根仓库 HEAD 为准，不看各子模块工作区当前停在哪。不会切换本地分支，也**不会强制推送**。

推送前会先检查：远端没有这条分支、已经是同一提交、或只是快进（远端历史仍包含在你要推的提交里）时才允许；远端已经分叉则拒绝。有正在进行的合并/变基时也会直接失败。

界面可以先「仅检查」；正式发布时通常会再让你确认要推哪些仓库。仅检查**不会**推送、也**不会**创建本地分支，但检查前仍会执行 `git submodule update --init --recursive`，可能初始化缺失的子模块并把已有子模块工作区对齐到根仓 HEAD 记录的 gitlink。子模块会从最内层开始推，避免根仓库指着一个远端还不存在的子模块提交。检查阶段只验证每一层自己能不能推，**不会**因为「子模块将在同一次发布里先推」而失败。父仓库引用的子模块提交如果还不在任何远端上，确认时必须一并勾选。

### 发布里最关键的 Git 命令

| 命令 | 一句话说明 |
|---|---|
| `git submodule update --init --recursive` | 先把子模块工作区按根仓库记录补齐，再统计要推什么。 |
| `git push --dry-run --recurse-submodules=no` | 只检查这一层自己能不能推，不要求子模块提交已经在远端。 |
| `git push --recurse-submodules=check` | 真正推送（先内层后外层）；若父仓库引用的子模块提交还没在远端，会先拦住。 |

---

## 使用提示

- 合并不等于发布：合并只在本地生成结果，要上远端请再走发布。
- 仓库脏了先清理，不要直接合并。
- 合并中途卡住时，优先「继续合并」或「终止合并」，不要一上来就清理（清理会丢掉未提交改动）。
- 发布填错目标分支可能把提交推到错误位置，请先确认分支名。
