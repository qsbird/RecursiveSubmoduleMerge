一

功能概览

合并
把来源分支合进工作分支
清理
把仓库恢复成可合并状态
发布
把结果推到指定远端分支

本工具用来处理「根仓库 + 多层子模块」的分支合并。界面上主要有三页：合并、清理、发布（把结果推到远端）。

仓库不干净时先清理，再合并；确认本地结果无误后再发布。

二

合并

把一条来源分支合进当前工作分支。工具会自动处理子模块指针冲突；普通文件冲突会打开你配置的冲突工具，让你手动改。

使用前：根仓库和所有子模块的工作区必须干净（没有未提交改动）。一次只合并一个分支。

大概过程

准备工作分支

按你选的基准创建或使用工作分支。

合入来源分支

把来源分支合进来。

处理冲突

子模块冲突由工具自动递归处理；普通文件冲突交给冲突工具。

生成提交

全部解决后，由工具生成合并提交。

必要时暂停

遇到工具无法自动处理的冲突时，会暂停并保留现场。你改完并执行 git add 后，点「继续合并」。不想继续则点「终止合并」。

「终止合并」只把本次合并涉及的仓库恢复到开始前，不会删除未跟踪文件。若要把整个仓库洗干净以便重新合并，请用「清理」。

合并里最关键的 Git 命令

命令一句话说明
git merge --no-ff --no-commit把对方分支合进当前仓库，先不自动提交，方便工具继续处理冲突。
git mergetool（或你配置的冲突工具）打开编辑器，帮你解决普通文件里两边都改过的内容。
git add把已经解决好的文件或子模块记入暂存区，表示“这里处理完了”。
git commit生成这次合并提交。工具会在冲突全部解决后自动执行，一般不必自己提交。
三

清理

破坏性操作 请先确认

未提交的修改、已暂存内容和未跟踪文件都可能被丢掉。需要保留的内容请先自行提交或另存。界面会要求确认；命令行非交互模式必须加 --yes。

和「终止合并」的区别

终止合并只撤销当前这一次合并；清理是整仓强力复位，不依赖是否正在合并，用来把脏仓库恢复成可重新合并的状态。

清理会递归处理根仓库和子模块，大致包括：中止进行中的合并/变基、把已跟踪文件打回最近一次提交、删掉多余未跟踪文件，再按当前提交把子模块对齐。某一步不够干净时，会自动用更强的方式再试。

可选：清理后重建工作分支。默认还会删掉上次暂停留下的 merge_manual_todo.txt。

清理里最关键的 Git 命令

命令一句话说明
git merge --abort / git rebase --abort取消正在进行的合并或变基，回到该操作开始前。
git reset --hard HEAD丢弃已跟踪文件的未提交修改，工作区回到最近一次提交。
git clean删除未被 Git 跟踪的文件和目录（默认不删被忽略的文件）。
git submodule update --init --recursive按当前提交把各层子模块内容重新下载并对齐。
四

发布（推送）

把当前根仓库 HEAD，以及它记录的子模块提交，推到你指定的远端分支。

  • 发布以根仓库 HEAD为准，不看各子模块工作区当前停在哪。
  • 不会切换本地分支，也不会强制推送。
  • 远端没有这条分支、已经是同一提交、或只是快进时才允许推送；远端已经分叉则拒绝。
  • 有正在进行的合并/变基时，整次发布会直接失败。
  • 界面可以先「仅检查」；正式发布时通常会再让你确认要推哪些仓库。
  • 子模块从最内层开始推，避免根仓库指着一个远端还不存在的子模块提交。

发布里最关键的 Git 命令

命令一句话说明
git submodule update --init --recursive先把子模块工作区按根仓库记录补齐，再统计要推什么。
git push --dry-run只检查能不能推成功，不会真的改远端。
git push --recurse-submodules=check真正推送；若根仓库引用的子模块提交还没在远端，会先拦住。
五

使用提示

1

合并不等于发布：合并只在本地生成结果，要上远端请再走发布。

2

仓库脏了先清理：不要直接合并。

3

合并中途卡住：优先「继续合并」或「终止合并」，不要一上来就清理（清理会丢掉未提交改动）。

4

核对推送目标：发布填错目标分支可能把提交推到错误位置，请先确认分支名。
